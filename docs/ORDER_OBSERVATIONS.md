# Live order observations and recovery

Account visibility and strategy ownership are separate. Schwab account-wide reads remain available, but a matching display name or tag does not establish ownership. Local submission, an explicitly restored instance checkpoint or a verified parent-child relationship does. Other adapters retain their account-history recovery contract.

Normal enabled variable backups include the broker's local order checkpoint. Automatic restoration requires an adapter-provided account identity. Without a launcher-set `order_ownership_id`, a strategy restores its own checkpoint when broker, account and strategy name match (a plain restart); with an id, the id must match as well, and a checkpoint written under an id is never restored without it. Open account orders that are neither placed in this run nor restored are never adopted; Schwab names them once in a warning. Two running instances with the same name sharing one variable store are unsupported. Applications that manage their own recovery can use `broker.export_order_state(strategy)` and `broker.restore_order_state(state, strategy)` before account reconciliation. Keep each checkpoint with the same instance and account. Applications should assign a stable, distinct `broker.order_ownership_id` before restoring; recovery rejects a checkpoint from a different bound instance, even with the same display name. Separate instances also need separate persistence locations/keys: the existing legacy variable database is keyed by display name. A shared display-name database row is not a durable multi-instance store. No ownership is inferred from that name. The existing backup cadence is unchanged; a crash before the next checkpoint can still leave a submission outcome unresolved. Never substitute account history for a checkpoint or assume an uncertain submission failed.

Live fill logs show this event's quantity, cumulative local fills, the broker-reported filled count when supplied, and observation source. Schwab activity wakes a REST read; its source is consequently REST, not streaming fill data. Contradictions log warnings without changing trading decisions.

Health distinguishes fill callbacks enqueued from actual strategy callback entries; queue delivery is not strategy execution. Existing telemetry includes `order_health`, and normal cleanup logs `[OrderRunHealth]`. Feed availability covers observed subscription time. Iteration median uses the most recent 1,024 samples; maximum and count cover the run. An iteration is not necessarily a complete basket scan. Hedge count, complete basket duration and deadline-to-dispatch delay remain null unless independently measured; HTTP cancellation duration is a different value.

Applications may override `Broker.on_order_observation(self, *, order, payload, source)` to retain evidence. Schwab invokes this hook for REST observations. The default stores nothing and adds no service, network protocol, credentials or infrastructure. Applications own handling of private payloads; hook exceptions must not interrupt broker event processing. Other adapters can call the same hook when their original broker response is available. This hook alone does not establish capture for every broker.

Regression evidence is native local parsing, order reconciliation, callback queues, executor ownership boundaries and enabled state persistence. It does not establish live brokerage, hosted runtime, crash durability between backups or multi-process stream sharing.
