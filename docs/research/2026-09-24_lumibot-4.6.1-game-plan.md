# LumiBot 4.6.1 game plan: evals, tools, examples, BotSpot, and the story

Date: 2026-09-24. Branch `version/4.6.0`. Companion to
`2026-09-24_agent-eval-and-capability-audit.md`, which has the eval numbers.
This one covers everything else and ranks it.

## A correction first

I told Rob indicators were "most requested." I had no evidence for that and
should not have said it. What the evidence actually shows is that failures
cluster in **order lifecycle and exits**, not indicators. Indicators are cheap
to write and worth doing; they are not the top of the list. Ranking below is
corrected.

## 1. Say the differentiator out loud

Rob's instinct is right and it is the highest-leverage marketing change
available, because it is true and nobody else can copy it quickly.

**The claim:** every agentic trading framework stops at the decision. LumiBot
carries it through a deterministic risk gate into a real broker and leaves an
inspectable record.

**The evidence for it, from the 2026 literature:**

- A review of 20+ DeFi trading agents: "the most common failure mode was this:
  the strategy looks responsible at the LLM step, and then nothing checks
  anything between 'model said yes' and 'transaction broadcasted'." Their
  second-largest named gap was exits treated as an afterthought.
- *Agentic Quantitative Trading*, arXiv 2608.31041 (Aug 2026): systems "remain
  concentrated on signal discovery, while complete integration with portfolio
  construction, execution, and risk control is still uncommon," and strong model
  capability "does not reliably translate into trading performance under live
  market conditions."
- Singapore IMDA (Jan 2026) and NIST's AI Agent Standards Initiative (Feb 2026)
  both converge on identity, traceability, stoppability.

**Where to put it:**

1. README, directly under the existing execution headline: a short section
   called something like "The part everyone else skips," three bullets, with the
   arXiv citation. Attributed third-party citations are allowed and they are what
   make this credible rather than boastful.
2. Docs homepage, same block.
3. A docs page that shows the actual artifacts: a `*_agent_detail.parquet` trace,
   a risk gate refusing an order, and the audit trail. Showing the record beats
   describing it.

**Do not claim** anything about returns, and do not claim we satisfy IMDA or
NIST. Say the field named three requirements and point at the primitives we
have. That is honest and it is still a strong claim.

## 2. Institutionalize evals in the repo's own instruction file

Rob is right that this needs a rule, not good intentions. Add to LumiBot's
`AGENTS.md` and `CLAUDE.md`:

- **Every new agent tool ships with at least one eval.** A tool with no eval is
  not done. Twenty-seven tools landed in a day and one got an eval; that is the
  failure this rule prevents.
- **Every new eval must fail first**, for the reason a customer would see, and
  the red artifact is saved in `agent_eval_baselines/`.
- **Repeat policy, matching BotSpot Agent:** a new eval must pass **3 times in a
  row when it is created**. The ongoing gate runs it **once**. Rob named this and
  it is the right split: 3x proves the eval is not flaky, 1x keeps the loop cheap
  enough to actually run.

That last point needs a code change: `REQUIRED_CONSECUTIVE_PASSES = 3` in
`scripts/run_agent_evals.py:35` is currently a hard floor that raises if you ask
for fewer. Split it into `NEW_CASE_REQUIRED_PASSES = 3` and a gate default of 1,
and raise `--max-workers` from 3 to 8 since these calls are network-bound.

## 3. Look-ahead evals, and why they carry more weight than I first said

Rob's point sharpens this considerably and it changes the ranking.

LumiBot prevents look-ahead **mechanically** where it controls the data path.
It cannot do that when the agent reaches the open web, an arbitrary API, or a
browser session. The Pelosi strategy is the perfect example: a disclosure page
lists years of trades, the backtest clock is somewhere in the middle, and nothing
in the plumbing can tell whether the agent respected the clock. **Only the agent
can, and only an eval can prove it did.**

So this is not one eval family, it is the family that protects the product's
core claim in exactly the region where the mechanical guards end. Proposed cases:

1. **Browser, disclosure page.** Page lists filings before and after the clock.
   Agent must use only the earlier ones. (The `house_public_disclosures` tool now
   filters server-side; this eval covers the case where the agent reaches the page
   directly and the filter is not there to save it.)
2. **Browser, news page.** Article list spans the clock. Agent must not cite or
   trade on a future-dated headline.
3. **`http_request`, arbitrary JSON API.** Response contains rows after the
   clock. Agent must filter.
4. **`rss_fetch`.** Feed carries future items. Same rule.
5. **Mixed source.** Two tools, one clean and one dirty, and the agent must not
   let the dirty one leak into the decision.
6. **Reporting honesty.** When the only available evidence is after the clock,
   the agent must say it cannot decide rather than use it.

Each of these needs the skill and system prompt to teach the rule, not just the
eval to check it. Evals and prompts ship together.

## 4. Whole-strategy evals

Rob's idea, and it is a good one because it tests the thing customers actually
do. Short prompt, skills do the work, end-to-end check:

- "Trade SPY using an opening range breakout."
- "Trade NVDA based on VWAP."
- "Buy TQQQ when it is above its 200 day average, otherwise hold cash."
- "Sell a SPY iron condor for this week."
- "Rebalance to 60/40 SPY and TLT."

Each asserts the agent picked the right structure, used the right tools, placed
a coherent order, and did not invent data. These double as the best possible
documentation: if "trade NVDA based on VWAP" just works, that is the demo.

## 5. Swappable system prompt and skills: a real gap, and a real feature request

Someone asked Rob for this. **It is not supported today.**

`agents.create()` takes `include_builtin_tools: bool = True` and
`include_builtin_skills: bool = True`. Those are on/off switches. There is no
way to point at your own skills directory, and the base prompt is assembled by
the private `_base_system_prompt` and `_compose_system_prompt` in
`manager.py`. So a user can turn LumiBot's skills off entirely and get nothing,
or leave them on and get ours. There is no middle.

What it should support:

- `skills_dir=` or `skills=[...]` to load the user's own skill files
- `base_system_prompt=` to replace ours, and a documented way to *extend* rather
  than replace, which is what most people actually want
- A documented, versioned description of what our base prompt contains, so a
  user can make an informed decision about replacing it
- The shipped skills as readable files people can copy and edit as a starting
  point (there are only three today: options-trading, research-data,
  stock-trading)

This is a small API change with a large trust payoff. Forcing a prompt on people
who are building trading systems is the kind of thing that makes an engineer
choose a different library.

## 6. Exits and rebalancing

The literature names exits as the second-largest gap, and Rob is right that
rebalancing belongs with it. Both are "get out of a position correctly."

- **Attach-at-placement brackets.** Take-profit and stop submitted with the entry
  so the venue enforces them and the agent does not have to stay awake. The ORB
  work on Sept 24 did this by prompt; it should be a primitive.
- **An exit watcher that reports when it dies.** The named failure mode is the
  background loop that stops silently.
- **A rebalance primitive.** Target weights in, orders out, with the drift
  threshold and the cash check handled once instead of re-derived per strategy.
- **A deterministic policy check the model cannot argue with.** Position caps,
  notional caps, symbol allowlist, evaluated after the model proposes and before
  the order goes out. This is the risk gate from section 1, made explicit.

Evals for each, including the case where the agent is instructed to breach a cap
and must refuse.

## 7. New tools worth adding

Rob asked what else besides evals. Ranked by how many strategies they unlock.

1. **Search.** The biggest missing primitive. The agent can fetch a URL and drive
   a browser but cannot find one. Options: DuckDuckGo through `ddgs` needs **no
   key at all** and should be the default; Exa, Tavily or Brave as opt-in upgrades
   for people who want better results.
2. **More key-free public data, wired in out of the box.** SEC and House
   disclosures are done. Still missing and all free without keys: Treasury
   FiscalData, CFTC Commitments of Traders, Federal Register, BLS. Each is a few
   hours and each unlocks a category of strategy.
3. **Earnings calendar and transcripts.** Repeatedly requested in this space.
   Motley Fool serves transcripts server-rendered, so `http_request` reaches them
   today; a dedicated tool makes it one call.
4. **A portfolio analytics tool.** Exposure, concentration, correlation and
   drawdown as a tool call, so the agent can check its own book before adding to
   it. Feeds directly into the rebalance and risk-gate work.
5. **Vendor marketplaces** such as FactSet. Genuinely interesting, but it needs a
   test account before anything is promised. Do not scope this until one exists.

## 8. Fewer API keys, concretely

Rob asked what I would actually do. Three things, in order:

1. **Make Alpaca the one key that unlocks the most.** A free Alpaca paper account
   already gives stocks, options history from Feb 2024, and news. That matches the
   direction already recorded in the workspace rules: backtest data should come
   from the customer's broker. So the first-run story becomes "open a free Alpaca
   account, paste one key, everything works," instead of four keys.
2. **Default every discovery tool to a key-free source.** Search via DuckDuckGo,
   public data via the no-key APIs above. Keys become upgrades, never
   prerequisites.
3. **Make the CLI tell you what you actually need.** `lumibot doctor my-bot`
   reads the strategy, names the keys that strategy requires and nothing else,
   and says which are already set. Today a user discovers a missing key by
   crashing.

The honest constraint: a model key is unavoidable for an AI strategy. Everything
else can be optional, and `lumibot demo` already runs with no key at all, which
is the right first impression.

## 9. Examples, BotSpot, and the marketplace

Read from the Sept 24 Codex handoff at
`docs/research/2026-09-23-ai-strategy-backtests/HANDOFF_AND_GAME_PLAN.md`.

Current state: the AI examples backtest correctly on Luna except Citadel and Ray
Dalio, which were rerun and are recorded but not re-verified as a set. **Nothing
is live on BotSpot**, because every BotSpot copy still runs old code and the new
examples import helpers that only exist in `version/4.6.0`. That is a factual
dependency: BotSpot runs a released LumiBot, and 4.6.0 is not released. The
entire "examples on BotSpot with links from the docs" chain sits behind it.

What the chain looks like once that is unblocked, per example:

1. Code current in the repo and green in a backtest on Luna
2. Copy updated on BotSpot through the owner MCP, new revision
3. Backtest run on BotSpot, `stats.csv` checked for negative cash, trades checked
   for sizing
4. Republished to the marketplace only if it passes
5. Docs page links to the BotSpot listing, and the listing links back to the docs
6. No Python business logic in the file: two or more agents, nothing between them

Two listings are already public with no backtest behind them, "SPY 1DTE AI Iron
Condor" and "Diversified Leveraged ETF ORB". Both are mine from Sept 18. They
should either get a passing backtest or come down; a public listing with no
evidence is the kind of thing that costs credibility exactly when someone senior
is looking.

## 10. Ranked for 4.6.1

By what most grows the library and most reduces the chance of hurting someone.

1. **Say the differentiator, in the README and the docs homepage.** Hours of
   work. It is the single highest-leverage change available and it needs no code.
2. **Eval policy in AGENTS.md, plus repeat 1 for the gate and 3 on creation, plus
   more workers.** Makes every item below cheap enough to actually happen.
3. **Order lifecycle evals.** Every asset class flows through orders; this is
   where a bug costs money.
4. **Look-ahead evals across browser, http, and rss.** Protects the core product
   claim precisely where the mechanical guards stop.
5. **Swappable system prompt and skills.** A real user asked. Small API change,
   large trust payoff, and it removes a reason to pick a competitor.
6. **Search tool, key-free by default.** The biggest missing primitive, and it
   directly reduces key fatigue.
7. **Exit and rebalance primitives, with their evals.** The field's two named
   gaps.
8. **Whole-strategy evals.** Doubles as the best demo material we could have.
9. **Examples through to BotSpot and the marketplace**, once the release
   dependency clears.
10. **Indicator evals.** Cheap, useful, and not the emergency I implied earlier.
11. **Remaining eval families** to roughly 60 cases.
12. **More key-free data sources**, one at a time.
